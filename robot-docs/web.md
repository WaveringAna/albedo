# web client

`web/` is the browser client: a canvas (Svelte 5, Svelte Flow) where sessions open as panels. It is a client like the TUI, not an extension; it reads the same daemon HTTP API.

`albedo web` (`cli/internal/cli/web.go`) finds or starts the daemon, serves `web/dist` (or `ALBEDO_WEB_DIST`, which the Nix package sets to its `web` build, `.#albedo-web`: `buildNpmPackage` over `web/`, so bump `npmDepsHash` in `default.nix` when `package-lock.json` changes) on `127.0.0.1:4317` (`--port`, 0 for any), prints a launch link and opens it unless `--no-open` or `ALBEDO_NO_BROWSER` is set. `cli/internal/webui` owns the boundary:

- The daemon token never reaches the browser. The page calls `/api/...` on its own origin; the proxy strips `/api`, drops `Origin`, `Cookie` and `Referer`, and adds `Authorization: Bearer <token>`. Session streams pass through unbuffered.
- Each run draws a launch key. `/?key=<key>` sets an `HttpOnly`, `SameSite=Strict` cookie and redirects to `/`; `/api` without that cookie answers `401 web_signed_out`. A restarted `albedo web` signs every tab out.
- Requests whose `Host` is not `127.0.0.1` or `localhost` are refused (DNS rebinding), and so is an `Origin` other than the page's own.
- A transport failure or a 401 from the daemon triggers `Connection.Refresh`, so a restarted daemon is found on the next request.
- `/assets/*` (content-hashed by Vite) is cached as immutable; everything else is `no-cache`.

In development, `npm run dev` in `web/` proxies `/api` the same way from `$ALBEDO_HOME/daemon.json`, read once at start (only when serving, so a build needs no daemon), dropping `Origin` and `Cookie`. It listens on the local network, open, so other devices at home can try the client; the `Host` it answers is limited to the machine's own name (bare and `.local`) and Tailscale's `*.ts.net`, since the proxy holds the token and a rebound name must not reach it.

Words: a **board** is a named canvas of panels, and the open boards are the tabs along the top (`boards.svelte.ts`). A board holds sessions from any folders. **Workspace** keeps its albedo meaning, a session's folder, and the sidebar shows each session's folder under its name. `+` makes a new board; double-click or F2 renames one; closing a tab keeps the board, which the palette reopens (`Open board: <name>`); `Delete board` removes it. The last tab cannot be closed, so there is always a canvas.

A board is an open canvas. **Windows** sit anywhere on it; the view pans freely and zooms out to an overview. Svelte Flow draws, drags and resizes the windows; `board.svelte.ts` places new ones (right of the selected window, top-aligned, stepping past overlaps) and owns the viewport. The wheel is handled in `Canvas.svelte` rather than by Svelte Flow, because windows and canvas share the trackpad: a pinch (ctrl-wheel) zooms around the pointer anywhere, an up-down scroll over a window that can scroll scrolls it while the zoom is readable (60% and up), and every other scroll pans. + and − zoom in and out by 5 points (the buttons too), ⇧1 fits all windows, ⇧0 returns to 100%, M shows an overview map, ⌥←/⌥→ moves between windows. The view controls (zoom, fit, map) fade in while the view moves and fade out 4 s after it stops; hovering or focusing them keeps them, and once faded they let clicks through to the windows beneath. What a window shows is a **view**, each framed by `nodes/WindowFrame.svelte`: a session's chat, or a review of one turn's changes; files, terminals and agent-made pages are meant to follow. A view opened from a window names it as its `parent`, opens beside it, and the canvas draws a faint dashed line between them (the board derives Svelte Flow edges from those parents; every window carries invisible handles for them).

The review (`nodes/ReviewNode.svelte`, `review.ts`) opens from "review N files +a −r" on a turn's sign-off, or from the +a −r on any work line, which also scrolls it to the first file that stretch of work changed (`data.jump`). It needs no daemon support beyond history: every tool call's trace records each file it changed, with the unified diff (`changes[].diff`, or `reason` when the file was binary, unreadable or too large). Writes the harness makes for itself stay out of it (`albedo_trace.unobserved()`): the browser plugin's profile lock and marker and its auto-named `.browser-artifacts` screenshots among them; a screenshot saved to a path the cell chose is still the cell's change. The window keeps the session, the turn and the turn's first history position, reads that turn's entries (`after=`, until the next turn starts), hydrates their traces, and shows the files with their counts, then each file's diffs in order. Diffs are drawn by `@pierre/diffs` (Shiki highlighting, `pierre-dark`/`pierre-light` tokens over the canvas's own ground and diff colours; `views/DiffView.svelte`), loaded with the first review so the rest of the client stays small. The margin button beside a line (drag for several) leaves a note on the canvas beside the window, tied to those lines; "send review" sends every unsent note tied into the review as one message, after an optional overall line.

Design rules the client keeps (from the design pass): surfaces separate by a step in tone, not by lines; only what floats (windows, the palette, the view controls, the overview map) casts a shadow; one accent, albedo's mauve by default and editable, used for focus and selection; no status dots; monospace only for code and tool commands.

The client shares the terminal's voice. `moods.ts` is a port of `cli/internal/tui/moods.go` (its pools, their order and the seeded FNV-1a pick), so a finished turn signs off with the same kaomoji in both clients: its seed is the turn's last entry time in milliseconds, and its class comes from how long it took. A busy session shows an animated face for what it is doing, read from its phase (`preparing`, `generating`, `running` a tool, `compacting`, `interrupting`; only `idle` and `interrupted` are at rest) and the tail of its activity, on one shared 500 ms clock for every face on the page (`live.svelte.ts`). Every frame of the animation sits invisibly under the current one, so a face keeps its width and nothing beside it moves. `burst.ts` writes a turn's thinking and tool calls as the terminal's one past-tense line (`thought 12s · read tui/{chat,moods}.go · ran go test ×2  +12 −3`), from each call's trace, fetched when the line scrolls into view. Speakers are named as in the terminal: "albedo" in mauve, "you" in teal, with "2h later" after a pause of 30 minutes or more. Copy is lowercase, and empty and error states carry a face. The canvas has sparse, faint dots that fade out below 75% zoom, before they can crowd into a texture.

Markdown (`markdown.ts`) also understands maths and diagrams: `$…$`, `\(…\)` and `$$…$$` / `\[…\]` (a dollar amount like "$5 or $10" stays prose: the opening `$` must touch its text and no digit may follow the closing one) and ```` ```mermaid ```` blocks. They render as placeholders carrying their source, and `enhance.ts` draws them after the message mounts: KaTeX for maths (`trust: false`), Pele (pele.run) for diagrams, themed with `--pele-*` from the canvas tokens, its SVG kept to drawing (no scripts, foreign objects, event attributes or outside links). Both load only when a message needs them.

**Notes** (`nodes/NoteNode.svelte`, `anchors.ts`, `notes.ts`, `Tethers.svelte`) are small text boxes on the canvas, saved with the board. Double-click empty canvas or press N for a loose one; the composer's pop-out button moves the draft into a note tied to its chat, for writing at length. Dragging a note's grip onto something ties the note to it: a window, a message or step in a chat (`data-entry`), or a line in a diff (found by the diff's `data-diff` key and the row's number inside Pierre's shadow root); dropping it on empty canvas sets it loose. Until a chat's first page is in and scrolled to its end, the thread stays hidden behind a skeleton shaped like the end of a typical chat (measured at phone width: a work line, a message, more work, the reply's last lines and its sign-off), so it never shows its top and then jumps. Tables in messages scroll sideways instead of squeezing their columns. A review names each file by its last two path segments (`…/chat/Chat.svelte`), the full path as its title.

While the grip is dragged, what it would land on is outlined (`pick` in `anchors.ts`); the drag follows the pointer on the whole document, so a note redrawn mid-drag, or dismissed, never leaves the tie or its outline behind. The target and a quote of it (the diff lines, or the message's first 600 characters) are kept on the note, so what it was about survives scrolling and closing. A line runs from each tied note to its target, and a target that is a passage (diff lines, a message, a step) is tinted while on screen; the note in hand, selected or under the pointer, draws its line and tint strongest. The line is measured in screen space every frame while any note is tied, held inside the window and whatever scrolls it. Notes float above windows (`zIndex`). A tied note sends on its own (⌘↵), from its chat's "send N notes" button, or with its review; notes for one session go as one message, each quoting what it was tied to (a note tied to a chat window itself is just a message). Sent notes stay on the board, quieter, until dismissed.

On a narrow screen (760 px or less) the client is a plain chat app unless settings ask for the canvas (`canvasOnPhone`): `layout.svelte.ts` and `Phone.svelte` show the session list, then one session's chat filling the screen, with a back button and the browser's back between them (`history.pushState`). There a review opens inside the chat, under the line that asked for it (`views/ReviewView.svelte`, the review window's body too), and notes and pop-out are off. The phone's session list and drawer are one picker (`SessionPicker.svelte`): up to six tiles (pinned, then sessions opened three or more times, most first, then today's), every other session as a list under them (three dots between the two, and every other row takes a softer step of the tiles' tone, so the stripes don't read as tiles), and a search field with a new-session button docked at the bottom on the ground's tone, within thumb reach; while searching it is all list. The phone's chat reads at 16 px unscaled with narrow margins, its composer floats over the thread (which scrolls on under it and ends clear of it), a chat has no bar and takes no gesture from the browser: a handle floating above the composer raises the session picker as a drawer over the chat. The drawer and the composer are one surface: the handle is the sheet's top edge, resting there when closed, and the sheet stands on the composer's bottom edge rather than the page's, so nothing of it reaches under what floats there (Safari's toolbar) and its search lands where the composer was. Dragging it up (or a quick swipe up from the composer itself, unless it would scroll the draft or follows a hold) raises the sheet with the finger while the composer fades into the search bar pinned in its place; dragging it down from its grip, or from anywhere while its list is at the top, lowers it. Let go and it settles open when past half (lowering: while still two thirds up) or flicked up, and otherwise sinks back into the composer; settling tweens the same number a finger moves, so the sheet, the composer's fade and the scrim stay one motion. A tap on the handle opens it, and a tap on its grip or above it, or choosing a session, closes it, and the browser's back still returns to the list, and the composer is one row (picture, field, stop, send; the working note moves into the placeholder).

**New session** (`NewSession.svelte`; the sidebar's "new session", the phone list and ⌘K): pick the folder from the folders sessions have used (`GET /workspaces`, ranked as you type), type a path, or browse to one (`GET /workspaces?location=`); then the provider profile (`GET /settings?group=providers`, starting on the default), its model (`GET /models?provider_profile=`) and effort, starting on the profile's own. Start is `PUT /sessions/{uuidv7}` with `If-None-Match: *` and `{kind: "new", workspace, provider_profile, model, effort}`, and the session opens.

**Model picker** (`chat/ModelPicker.svelte`, sharing `ModelChoice.svelte` with new session): the composer shows the session's model and effort as a chip; it opens a pane to switch the provider profile, model and effort, which reads the session's configuration for its validator and sends `PATCH /sessions/{id}?view=configuration` as a merge patch with `If-Match`. It applies from the next turn.

**Slash commands** (`commands.ts`): the chat reads the session's commands from `GET /sessions/{id}/catalog?kind=commands` (only those a human may call; the list is empty until the session's runtime has loaded once). Typing `/` in the composer lists them, filtered as you type (arrows, Tab or Enter to complete, Escape to clear). A line starting with a command runs it: arguments are read the way the terminal reads them (words in order, the last taking the rest, or a JSON object), and one name that is both a read and a change picks the read when nothing follows it. Skills and command inputs are sent as `{kind: "command"}` inputs; reads and changes are the daemon operations the catalogue declares, with path, query, headers and body bound from the session record, the arguments or literals, and their answer shows above the composer until dismissed.

The (?) beside the wordmark opens an about pane (`About.svelte`): a one-line description (a placeholder for now), the main contributors with their Bluesky handles, thanks to everyone else with a link to the full history on tangled, and the libraries the client is built on with their licences, linking `THIRD_PARTY_NOTICES.md`.

Settings (the sliders button at the top right, or ⌘,) is a non-modal pane over the board: the theme (follow the system, the default; light; dark), each mode's colours, and the canvas dots. A mode's colours are three seeds and a contrast, as in the Codex app: accent, background (the ground), foreground (the ink) as hex, with a native picker beside each, and contrast from 0 to 100; accent presets fill the accent for the mode being edited, and a theme copies and pastes as JSON (both modes, or one palette for the mode being edited). `app.css` derives every other token from the seeds with `color-mix` in OKLab (surfaces, chrome, fields, secondary text, hover, dots, shadow tint) and relative `oklch()` (the brand's second stop, and "you" opposite the accent), so any three colours make a whole theme; contrast scales how far each step goes. The colours are [madoromi](https://madoromi.moonwit.ch/)'s (MPL-2.0, credited in the pane and in `THIRD_PARTY_NOTICES.md`): the defaults are its spring, haru, by day (`#f6eff8` paper, `#584a5c` ink, `#6928bd` wisteria) and by night (`#241c26`, `#e1d1e7`, `#ddb3ff`); its four seasons set both modes at once, keeping each mode's contrast, and the accent presets are its spring inks. Preferences live in this browser (`prefs.svelte.ts`, `albedo.prefs.v4`, carrying the theme and dots over from earlier keys) and in an `albedo_prefs` cookie, which every port on the host shares, so the dev server and each `albedo web` port open the same way; the cookie wins when both exist, and `albedo web` drops it before forwarding to the daemon. Settings also take an interface and a code font by name (a comma adds fallbacks; each name is quoted and nothing that could end the value survives, see `fontStack`), set as `--sans` and `--mono` on `<html>` ahead of the default stacks; where the browser offers `queryLocalFonts`, the installed families are suggested. The resolved mode is `data-theme` on `<html>` and its seeds are inline custom properties there; a small script in `index.html` applies both before the first paint, and `prefs` follows system changes while the theme is `system`.

The chat view (`chat/`) reads `GET /sessions/{id}/history` (newest page, then `before=` as the reader scrolls up, and `after=` when the stream says something committed) and sends with `PUT /sessions/{id}/inputs/{uuidv7}`; while the session works, a stop button beside send (or Escape in an empty field) reads the session's `run_id` and `input_order` fresh and posts `/sessions/{id}/interrupt`, so a stop never reaches a later run, `{kind: "message", text}`; images attach by paste, drop or the composer's picture button (`chat/attachments.ts`, the terminal client's scheme: each image leaves an `[Image #n]` marker at the cursor, deleting the marker drops the image, sending renumbers the marked images 1..n in reading order and sends them base64 as `images`, at most 10); a user entry's images show above its bubble from their history references (`/api/sessions/{id}/history/{entry}/image-n`). a send stays on screen as pending until its `input_id` appears in history, and a failed one offers retry with the same id. Your newest message carries a receipt until a reply follows it, drawn as Signal's (`chat/Receipt.svelte`): a dashed ring while sending, a ring with a check once the daemon has accepted it (sent), two filled ones once its entry is in history (seen), which the daemon commits in the same transaction that takes it into the conversation, so the model has it (a message sent while albedo works stays `sent` until the loop takes it at its next step). Until it is seen the bubble stays faded. A waiting input is not listed anywhere, so after a reload it shows nothing until it commits. `transcript.svelte.ts` turns entries into blocks: user bubbles, assistant markdown, and each run of thinking and tool calls between messages folded into one "Worked" line (open while it is the live run). Referenced message text is fetched with the page; tool arguments and output only when their run is opened. Markdown is rendered by `marked` with raw HTML escaped and only http(s)/mailto links (`markdown.ts`), because transcripts carry model and tool text into a page that can reach the daemon. The session list (`sessions.svelte.ts`) follows the collection's stream (`GET /sessions?scope=roots` as server-sent events, `followSessions` in `stream.ts`): each `activity` event patches that session's status and activity in place, so the sidebar, window titles and faces change as the daemon does, and `reset`, `overflow` or `invalidate` reads the list again (once for a burst). While that stream is up the list is also read once a minute in case; while it is down, every 4 s. Both stop while the tab is hidden.

Each chat also follows the session's event stream (`stream.ts`: `GET /sessions/{id}?tail=0` as server-sent events, read with `fetch` so it can resume with `after_generation` and `after_seq`, backing off from 0.5 s to 5 s). Thinking and reply deltas show as they are written, tool progress shows as a running step until its call commits, and status events drive the faces ahead of the session list. A reset carries a snapshot whose `active_output` and `current_progress` restore what was in flight. A `committed` event reads the new history first and then drops the live output it names, so a reply never blinks out between its last delta and its entry. While the stream is down the chat falls back to polling every 1.2 s while busy and 5 s otherwise; while it is up, every 20 s.

Boards live in the browser's `localStorage`: the list under `albedo.boards.v1`, and each board's windows (position, size, what they show) and viewport under `albedo.board.v2:<id>`. Only the active board is mounted; `FlowBinder` hands it the flow helpers, and anything asked of a hidden board (revealing a new window) runs when it is shown.

Checks: `npm run check` and `npm run build` in `web/`; `go -C cli test ./internal/webui/` for the boundary. Neither web command is in `test.sh` yet, because the dev shell has no Node.
