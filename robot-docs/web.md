# web client

`web/` is the browser client: a canvas (Svelte 5, Svelte Flow) where sessions open as panels. It is a client like the TUI, not an extension; it reads the same daemon HTTP API.

`albedo web` (`cli/internal/cli/web.go`) finds or starts the daemon, serves `web/dist` (or `ALBEDO_WEB_DIST`) on `127.0.0.1:4317` (`--port`, 0 for any), prints a launch link and opens it unless `--no-open` or `ALBEDO_NO_BROWSER` is set. `cli/internal/webui` owns the boundary:

- The daemon token never reaches the browser. The page calls `/api/...` on its own origin; the proxy strips `/api`, drops `Origin`, `Cookie` and `Referer`, and adds `Authorization: Bearer <token>`. Session streams pass through unbuffered.
- Each run draws a launch key. `/?key=<key>` sets an `HttpOnly`, `SameSite=Strict` cookie and redirects to `/`; `/api` without that cookie answers `401 web_signed_out`. A restarted `albedo web` signs every tab out.
- Requests whose `Host` is not `127.0.0.1` or `localhost` are refused (DNS rebinding), and so is an `Origin` other than the page's own.
- A transport failure or a 401 from the daemon triggers `Connection.Refresh`, so a restarted daemon is found on the next request.
- `/assets/*` (content-hashed by Vite) is cached as immutable; everything else is `no-cache`.

In development, `npm run dev` in `web/` proxies `/api` the same way from `$ALBEDO_HOME/daemon.json`, read once at start.

Words: a **board** is a named canvas of panels, and the open boards are the tabs along the top (`boards.svelte.ts`). A board holds sessions from any folders. **Workspace** keeps its albedo meaning, a session's folder, and the sidebar shows each session's folder under its name. `+` makes a new board; double-click or F2 renames one; closing a tab keeps the board, which the palette reopens (`Open board: <name>`); `Delete board` removes it. The last tab cannot be closed, so there is always a canvas.

A board is an open canvas. **Windows** sit anywhere on it; the view pans freely and zooms out to an overview. Svelte Flow draws, drags and resizes the windows; `board.svelte.ts` places new ones (right of the selected window, top-aligned, stepping past overlaps) and owns the viewport. The wheel is handled in `Canvas.svelte` rather than by Svelte Flow, because windows and canvas share the trackpad: a pinch (ctrl-wheel) zooms around the pointer anywhere, an up-down scroll over a window that can scroll scrolls it while the zoom is readable (60% and up), and every other scroll pans. ⇧1 fits all windows, ⇧0 returns to 100%, M shows an overview map, ⌥←/⌥→ moves between windows. What a window shows is a **view**: today a session's chat; files, diffs, terminals and agent-made pages are meant to be further views beside it, each framed by `nodes/WindowFrame.svelte`.

Design rules the client keeps (from the design pass): surfaces separate by a step in tone, not by lines; only what floats (windows, the palette, the view controls, the overview map) casts a shadow; one accent, albedo's mauve by default and editable, used for focus and selection; no status dots; monospace only for code and tool commands.

The client shares the terminal's voice. `moods.ts` is a port of `cli/internal/tui/moods.go` (its pools, their order and the seeded FNV-1a pick), so a finished turn signs off with the same kaomoji in both clients: its seed is the turn's last entry time in milliseconds, and its class comes from how long it took. A busy session shows an animated face for what it is doing, read from its phase (`preparing`, `generating`, `running` a tool, `compacting`, `interrupting`; only `idle` and `interrupted` are at rest) and the tail of its activity, on one shared 500 ms clock for every face on the page (`live.svelte.ts`). Every frame of the animation sits invisibly under the current one, so a face keeps its width and nothing beside it moves. `burst.ts` writes a turn's thinking and tool calls as the terminal's one past-tense line (`thought 12s · read tui/{chat,moods}.go · ran go test ×2  +12 −3`), from each call's trace, fetched when the line scrolls into view. Speakers are named as in the terminal: "albedo" in mauve, "you" in teal, with "2h later" after a pause of 30 minutes or more. Copy is lowercase, and empty and error states carry a face. The canvas has sparse, faint dots that fade out below 75% zoom, before they can crowd into a texture.

Settings (the sliders button at the top right, or ⌘,) is a non-modal pane over the board: the theme (follow the system, the default; light; dark), each mode's colours, and the canvas dots. A mode's colours are three seeds and a contrast, as in the Codex app: accent, background (the ground), foreground (the ink) as hex, with a native picker beside each, and contrast from 0 to 100; accent presets fill the accent for the mode being edited, and a theme copies and pastes as JSON (both modes, or one palette for the mode being edited). `app.css` derives every other token from the seeds with `color-mix` in OKLab (surfaces, chrome, fields, secondary text, hover, dots, shadow tint) and relative `oklch()` (the brand's second stop, and "you" opposite the accent), so any three colours make a whole theme; contrast scales how far each step goes. The colours are [madoromi](https://madoromi.moonwit.ch/)'s (MPL-2.0, credited in the pane and in `THIRD_PARTY_NOTICES.md`): the defaults are its spring, haru, by day (`#f6eff8` paper, `#584a5c` ink, `#6928bd` wisteria) and by night (`#241c26`, `#e1d1e7`, `#ddb3ff`); its four seasons set both modes at once, keeping each mode's contrast, and the accent presets are its spring inks. Preferences live in this browser (`prefs.svelte.ts`, `albedo.prefs.v4`, carrying the theme and dots over from earlier keys). The resolved mode is `data-theme` on `<html>` and its seeds are inline custom properties there; a small script in `index.html` applies both before the first paint, and `prefs` follows system changes while the theme is `system`.

The chat view (`chat/`) reads `GET /sessions/{id}/history` (newest page, then `before=` as the reader scrolls up, and `after=` when the stream says something committed) and sends with `PUT /sessions/{id}/inputs/{uuidv7}` `{kind: "message", text}`; a send stays on screen as pending until its `input_id` appears in history, and a failed one offers retry with the same id. `transcript.svelte.ts` turns entries into blocks: user bubbles, assistant markdown, and each run of thinking and tool calls between messages folded into one "Worked" line (open while it is the live run). Referenced message text is fetched with the page; tool arguments and output only when their run is opened. Markdown is rendered by `marked` with raw HTML escaped and only http(s)/mailto links (`markdown.ts`), because transcripts carry model and tool text into a page that can reach the daemon. Each chat also follows the session's event stream (`stream.ts`: `GET /sessions/{id}?tail=0` as server-sent events, read with `fetch` so it can resume with `after_generation` and `after_seq`, backing off from 0.5 s to 5 s). Thinking and reply deltas show as they are written, tool progress shows as a running step until its call commits, and status events drive the faces ahead of the session list. A reset carries a snapshot whose `active_output` and `current_progress` restore what was in flight. A `committed` event reads the new history first and then drops the live output it names, so a reply never blinks out between its last delta and its entry. While the stream is down the chat falls back to polling every 1.2 s while busy and 5 s otherwise; while it is up, every 20 s.

Boards live in the browser's `localStorage`: the list under `albedo.boards.v1`, and each board's windows (position, size, what they show) and viewport under `albedo.board.v2:<id>`. Only the active board is mounted; `FlowBinder` hands it the flow helpers, and anything asked of a hidden board (revealing a new window) runs when it is shown.

Checks: `npm run check` and `npm run build` in `web/`; `go -C cli test ./internal/webui/` for the boundary. Neither web command is in `test.sh` yet, because the dev shell has no Node.
